# 12. 관리

관리자에게만 보이는 메뉴입니다. 왼쪽 메뉴의 **관리** 아래에 있습니다.

## 사용자

<p align="center"><img src="images/users.png" alt="사용자 목록과 사용자 추가" width="860"></p>

### 사용자 추가

1. 아래 **사용자 추가**에서 아이디(영문, 숫자, `.` `_` `-`)와 초기 비밀번호(10자 이상)를 적습니다.
2. 역할을 고릅니다: **멤버** 또는 **관리자**([역할 표](README.md#역할)). 기본값은 멤버입니다.
3. **추가**를 누르고, 정한 비밀번호를 본인에게 직접 전합니다. 본인은 로그인한 뒤 [내 계정](02-getting-started.md#내-계정)에서 비밀번호를 바꿉니다.

### 역할 바꾸기, 비밀번호 재설정, 비활성화

- **역할**: 목록의 역할 칸에서 바로 고릅니다.
- **담당 사이트**: 멤버마다 담당한 사이트 수가 보입니다. 숫자를 누르면 그 멤버의 사이트만 거른 [사이트 목록](04-sites.md#사이트-목록)이 열립니다. 담당자는 [사이트 화면](04-sites.md#사이트-담당자)에서 정합니다.
- **비밀번호 재설정**: 새 비밀번호(10자 이상)를 적고 **재설정**을 누릅니다. 본인에게 직접 전합니다.
- **비활성화/활성화**: 비활성화한 사용자는 로그인할 수 없습니다. 기록은 남습니다.

역할을 바꾸거나, 비밀번호를 재설정하거나, 비활성화하면 그 사용자는 바로 로그아웃됩니다. 활성 관리자는 최소 한 명 있어야 하므로 마지막 관리자는 바꾸거나 끌 수 없고, 자기 자신은 비활성화할 수 없습니다.

로그인에 5번 연속 실패한 계정은 **잠김**으로 표시되고 10분 뒤 저절로 풀립니다.

### 2단계 인증 해제

(v1.4.0부터) [2단계 인증](02-getting-started.md#2단계-인증)을 켠 사용자는 상태 칸에 **2단계 인증** 표시가 붙습니다. 그 사용자가 휴대폰과 복구 코드를 모두 잃었으면 **2단계 인증 해제**를 누릅니다. 그 사용자는 로그아웃되고, 다음에는 비밀번호만으로 로그인한 뒤 내 계정에서 다시 켤 수 있습니다. 자기 자신의 2단계 인증은 내 계정에서 끕니다.

## 감사 로그

누가 언제 무엇을 했는지 기록합니다. 로그인, 계정 잠김, 2단계 인증 켜기·끄기·해제, 사용자 추가·변경, 사이트 저장, 사이트 담당자 변경, 설정 파일 가져오기, 설정 적용·롤백, 드리프트 가져오기, 인증서 발급·갱신·업로드, nginx 시작·재시작·업그레이드, API 토큰 만들기·지우기가 남습니다. [API 토큰](#api-토큰)으로 한 일은 사용자가 `token:이름`으로 보입니다. 비밀번호와 키는 남기지 않습니다.

<p align="center"><img src="images/audit.png" alt="감사 로그" width="860"></p>

위의 조건으로 좁혀 찾습니다.

- **사용자**: 아이디가 정확히 같아야 찾습니다.
- **동작**, **결과**(성공, 실패)
- **시작일**, **종료일**: 두 날짜를 모두 포함합니다.

비워 둔 조건은 적용하지 않습니다. 인증서 자동 갱신처럼 사람이 하지 않은 동작은 사용자가 **시스템**으로 보입니다. 목록 아래 **← 최근**, **이전 →**으로 넘깁니다.

**CSV 내려받기**(v1.8.0부터)를 누르면 지금 조건에 맞는 기록을 CSV 파일로 받습니다. 최근 10,000줄까지 담기고, 엑셀에서 바로 열어도 한글이 깨지지 않습니다. 더 많이 필요하면 기간을 나눠 받습니다. `=`, `+`, `-`, `@`로 시작하는 값은 스프레드시트가 수식으로 읽지 않도록 앞에 `'`가 붙습니다.

## 알림 설정

운영 중에 생긴 일을 등록한 채널(메일, 웹훅)로 알립니다. **설정** 메뉴(또는 인증서 화면 위의 **알림 설정**)에서 정합니다.

| 알림 | 언제 |
| --- | --- |
| 인증서 | 발급·갱신에 실패했거나 만료가 가까울 때 |
| 적용 실패 (v1.8.0부터) | 설정 적용·롤백이 검증(`nginx -t`)에 실패했거나, 적용 뒤 상태 확인에 실패해 자동으로 되돌렸을 때, 끝나지 않은 적용을 시작할 때 되돌렸을 때 |
| nginx 내려감·재시작 (v1.8.0부터) | nginx 마스터 프로세스가 내려갔거나 다시 시작됐을 때. 업그레이드로 nginx 컨테이너가 다시 뜰 때도 옵니다 |
| 직접 바뀐 설정 파일 (v1.8.0부터) | 관리도구를 거치지 않고 서버에서 바뀐 설정 파일을 찾았을 때. 같은 변경은 한 번만 알리고, 바뀐 파일 목록이 달라지면 다시 알립니다([8장](08-versions.md)) |
| 백업 실패 (v1.8.0부터) | `nm backup`(자동 백업 포함)이 실패했을 때. 실패 한 번에 한 번 알립니다 |
| 계정 잠김 (v1.8.0부터) | 로그인(또는 2단계 인증 코드) 실패가 이어져 계정이 잠겼을 때 |

채널 목록의 **받을 알림**에서 채널마다 받을 종류를 고르고 **저장**을 누릅니다. 예를 들어 팀 Slack 웹훅은 모두 받고, 당번 메일은 적용 실패와 nginx 재시작만 받게 할 수 있습니다. 새로 추가한 채널과 v1.8.0 전에 만든 채널은 모두 받습니다. 모두 끄면 그 채널로는 **테스트** 알림만 갑니다.

<p align="center"><img src="images/notifications.png" alt="알림 채널 목록과 채널 추가" width="860"></p>

### 채널 추가

1. **종류**를 고릅니다.
   - **웹훅**: 알림마다 `event`, `subject`, `message`, `text` 필드를 담은 JSON을 POST로 보냅니다. `text` 필드가 있어 Slack 수신 웹훅 URL을 그대로 쓸 수 있습니다.
   - **메일**: 서버에 SMTP 설정(`SPRING_MAIL_*` 환경 변수, [1장](01-install.md#환경-변수))이 있어야 보낼 수 있습니다.
2. **대상**에 웹훅 URL 또는 받는 메일 주소를 적고 **추가**를 누릅니다.

### 채널 관리

- **테스트**: 그 채널로 시험 알림을 한 번 보냅니다. 설정이 맞는지 먼저 확인하세요.
- **사용/중지**: 채널을 지우지 않고 잠시 멈춥니다.
- **삭제**: 채널을 지웁니다.

웹훅은 서버가 관리자가 정한 URL로 요청을 보내는 기능이므로, 관리자 역할은 믿을 수 있는 사람에게만 줍니다.

## API 토큰

v1.9.0부터 배포 스크립트나 CI에서 관리도구를 부를 수 있습니다. 배포하는 동안 점검 모드를 켜고, 끝나면 끄는 일을 사람이 화면을 누르지 않고 합니다. **설정** 메뉴의 **API 토큰** 탭에서 토큰을 만듭니다(관리자).

1. **이름**에 어디서 쓰는 토큰인지 적고(예: `github-deploy`) **만들기**를 누릅니다.
2. 화면 위에 `nmt_`로 시작하는 토큰 값이 나옵니다. **이 값은 지금 한 번만 보입니다.** 바로 복사해 CI의 비밀 값(GitHub Actions secret 등)에 넣습니다. 관리도구에는 해시만 남아 다시 볼 수 없으니, 잃어버리면 지우고 새로 만듭니다.
3. 목록에서 토큰의 앞 몇 글자, 만든 사람, 마지막으로 쓴 때를 봅니다. **삭제**하면 그 토큰으로 오는 요청은 바로 거절됩니다.

<p align="center"><img src="images/api-tokens.png" alt="API 토큰을 만든 직후 화면과 토큰 목록" width="860"></p>

토큰은 관리자 권한으로 동작합니다. 꼭 필요한 곳에만 두고, 쓰지 않는 토큰은 지웁니다. 토큰으로 한 일은 감사 로그에 `token:이름`으로 남고(v1.9.1부터는 버전 이력의 작성자도 `token:이름`), 적용이 실패하면 [알림](#알림-설정)도 갑니다.

### API

요청마다 `Authorization: Bearer <토큰>` 헤더를 붙입니다. 답은 JSON입니다. 토큰이 없거나 틀리면 `401`입니다.

| 요청 | 하는 일 |
| --- | --- |
| `GET /api/v1/sites` | 사이트 목록. 사이트마다 `domain`, `type`, `enabled`, `maintenance`, `pending`, `https` |
| `POST /api/v1/sites/{도메인}/maintenance` | 본문 `{"enabled": true, "apply": true}`. 점검 모드를 켜거나(`true`) 끕니다(`false`). `apply`가 `true`면 바꾼 뒤 적용 대기 중인 변경을 모두 적용합니다. 이미 그 상태면 초안을 만들지 않습니다(`changed: false`) |
| `POST /api/v1/apply` | 적용 대기 중인 변경을 모두 적용합니다. 결과 `result`는 `SUCCESS`, `NOTHING_TO_APPLY`, `VALIDATION_FAILED`, `AUTO_RECOVERED` 중 하나입니다 |

- 적용이 검증에 실패하거나 자동으로 되돌렸으면 `422`와 함께 `errors`에 `nginx -t` 오류가 담깁니다. 스크립트는 HTTP 상태로 성공을 판단하면 됩니다(`curl --fail`).
- 본문이 없거나 JSON이 아니거나 `enabled`가 빠졌으면 `400`입니다. 오류는 모두 `{"error": "이유"}` 모양으로 옵니다.
- 없는 도메인은 `404`, Raw 설정 사이트의 점검 모드나 다른 적용과 겹친 요청, nginx 컨테이너 업그레이드가 필요해 적용이 막힌 때는 `409`입니다.

배포 스크립트 예:

```bash
NM=https://manager.example.com
AUTH="Authorization: Bearer $NM_TOKEN"

# 점검 모드 켜고 바로 적용
curl --fail -X POST -H "$AUTH" -H "Content-Type: application/json" \
     -d '{"enabled": true, "apply": true}' "$NM/api/v1/sites/app.example.com/maintenance"

./deploy.sh

# 점검 모드 끄고 적용
curl --fail -X POST -H "$AUTH" -H "Content-Type: application/json" \
     -d '{"enabled": false, "apply": true}' "$NM/api/v1/sites/app.example.com/maintenance"
```
