# 13. 문제 해결

## "nginx 컨테이너(에이전트)에 연결할 수 없습니다" 띠가 보일 때

관리 화면이 nginx 컨테이너 안의 에이전트에 연결하지 못하고 있습니다. 설정 검증과 적용이 멈춥니다.

1. `docker compose ps`로 `nginx` 컨테이너가 돌고 있는지 확인합니다. 멈춰 있으면 `docker compose up -d nginx`.
2. compose 파일에서 nginx 서비스 이름을 바꿨다면 manager의 `NGINX_RUNTIME_AGENT_URL`도 함께 바꿉니다.
3. 에이전트 토큰을 직접 정했다면 manager의 `NGINX_RUNTIME_AGENT_TOKEN`과 nginx의 `NGINX_AGENT_TOKEN`이 같은지 확인합니다.

## "API 판이 맞지 않아" 띠가 보일 때

관리 화면과 nginx 컨테이너가 서로 말이 통하지 않는 판입니다. 릴리스 버전만 다른 것은 정상이고 띠가 뜨지 않습니다. nginx 이미지도 함께 올립니다: `nm upgrade --nginx`([1장](01-install.md#업그레이드)).

## 관리 도메인이 열리지 않을 때

대시보드의 **관리 화면 도메인**에 상태와 이유가 보입니다. 그동안은 `http://127.0.0.1:9000`(SSH 터널)으로 들어옵니다.

먼저 서버에서 `sudo /opt/nginx-manager/nm check-domain`을 실행합니다. 도메인이 DNS에 있는지, `http://도메인`이 이 서버의 nginx로 들어오는지 확인해 알려 줍니다(`nm status`, `nm restart`, 설치 직후에도 저절로 확인합니다).

브라우저에 보이는 것으로도 어디서 막혔는지 알 수 있습니다.

| 보이는 것 | 뜻 |
| --- | --- |
| `404 Not Found` | 그 도메인을 맡은 설정이 없습니다. `.env`의 `NGINX_MANAGER_ADMIN_DOMAIN`이 비었거나 오타가 있는지(`nm status`에 보이는 주소) 확인하고 고친 뒤 `nm restart` |
| `HTTPS certificate is not ready yet` | 설정은 됐고 인증서를 기다립니다. 보통 1~2분 안에 HTTPS로 바뀝니다. 오래 가면 아래를 봅니다 |
| 접속이 안 됨 | DNS가 다른 서버를 가리키거나 방화벽이 80/443을 막습니다 |

- **인증서 발급을 기다리는 중**: 도메인의 DNS가 이 서버를 가리키는지, 인터넷에서 이 서버의 80 포트로 들어올 수 있는지(방화벽, 클라우드 보안 그룹) 확인합니다. 발급은 저절로 다시 시도합니다. `NGINX_HTTP_PORT`를 80이 아닌 값으로 바꿨다면 앞단이 `/.well-known/acme-challenge/`를 넘겨 줘야 합니다.
- **같은 도메인의 사이트가 있어 만들지 않았습니다**: 그 사이트를 지우거나 `.env`의 관리 도메인을 바꾸고 `nm restart`.
- **403**: `NGINX_MANAGER_ADMIN_ALLOW`에 지금 주소가 들어 있는지 확인합니다.

## 관리 화면이 뜨지 않을 때(manager가 unhealthy)

nginx는 따로 돌기 때문에 사이트는 계속 열립니다. 먼저 이유를 봅니다.

```bash
cd /opt/nginx-manager && sudo docker compose logs manager 2>&1 | grep -m5 -A3 -E 'Exception|Caused by'
```

`AccessDeniedException: /etc/nginx/...`가 보이면 서버에서 `sudo`로 만든 파일이나 디렉터리(root 소유)에 관리도구가 쓰지 못한 것입니다. v1.2.2부터는 manager가 시작할 때 소유자를 맞추므로 `sudo /opt/nginx-manager/nm restart`면 됩니다. 그 전 버전은 소유자를 직접 맞추고 다시 띄웁니다.

```bash
sudo chown -R 10101:10101 /opt/nginx-manager/data/conf
sudo /opt/nginx-manager/nm restart
```

적용이 끝나기 전에 끊겼다면 다시 뜰 때 적용 전 파일로 되돌립니다. 초안은 남아 있어 다시 적용할 수 있습니다.

## 적용이 "쓸 수 없어 적용하지 못했습니다"로 실패할 때

위와 같은 이유입니다. 서버에서 `data/conf` 아래에 파일을 직접 복사하거나 디렉터리를 만들었다면 `sudo /opt/nginx-manager/nm restart`로 소유자를 맞춘 뒤 다시 적용합니다. 직접 복사하기보다 [5장](05-import.md)의 가져오기를 쓰면 이런 일이 없습니다.

## nm upgrade가 "되돌렸습니다"로 끝날 때

새 관리 화면이 정해진 시간 안에 뜨지 않아 이전 버전과 업그레이드 전 DB로 되돌린 것입니다. nginx는 그대로 돌고 있습니다. 출력에 보인 로그 끝부분으로 이유를 확인하고, 느린 서버라면 `NM_WAIT_TIMEOUT=600 nm upgrade`처럼 기다리는 시간을 늘려 다시 합니다.

## 업그레이드 뒤 nginx가 뜨지 않을 때

새 nginx가 지금 설정을 받아들이지 않으면 nginx를 띄우지 않고 대시보드에 문제의 파일과 줄을 보여 줍니다. 두 가지 방법 중 하나로 고칩니다.

- **설정을 고치기**: 대시보드의 링크로 [설정 파일](10-files.md)을 열어 문제가 된 줄을 고치고 적용한 뒤, 대시보드의 **nginx 시작**을 누릅니다.
- **nginx를 이전 버전으로**: nginx 컨테이너를 바로 전에 쓰던 이미지 태그로 다시 띄웁니다. 볼륨의 설정과 데이터는 그대로 씁니다.

## 적용했는데 "문법 검증에 실패"했을 때

서버의 설정은 바뀌지 않았습니다. 결과에 보이는 파일과 줄을 고친 뒤 다시 적용합니다. 이번 초안이 바꾸지 않은 파일이 문제라면, 누군가 서버에서 직접 고친 파일일 수 있으니 [이력](08-versions.md#서버에서-직접-바뀐-설정)을 확인합니다.

## 적용했는데 "직전 설정으로 되돌렸습니다"가 나올 때

문법은 맞지만 reload 뒤 nginx 상태가 나빴습니다. 흔한 원인은 다른 사이트·스트림이나 다른 프로그램이 이미 쓰는 포트입니다. 원인을 고친 뒤 다시 적용합니다.

## Let's Encrypt 발급이 실패할 때

- 도메인(대표·추가 모두)의 DNS가 이 서버를 가리키는지 확인합니다.
- 인터넷에서 이 서버의 **80 포트**로 들어올 수 있어야 합니다(방화벽, 공유기 포트 포워딩, 클라우드 보안 그룹).
- 와일드카드 도메인은 Let's Encrypt 자동 발급(HTTP 인증)으로 받을 수 없습니다. 인증서를 [업로드](09-certs.md#인증서-업로드)합니다.
- 짧은 시간에 여러 번 실패했다면 운영 환경의 발급 횟수 제한에 걸렸을 수 있습니다. [스테이징](09-certs.md#lets-encrypt-설정)으로 먼저 시험합니다.

실패 사유는 사이트 화면과 인증서 목록에 보이고, 잠시 뒤 자동으로 다시 시도합니다.

## 스트림을 만들었는데 밖에서 접속이 안 될 때

nginx 컨테이너에서 그 포트를 열어야 합니다. compose 파일의 nginx `ports`에 포트를 더하고 `docker compose up -d nginx`로 다시 띄웁니다([6장](06-streams.md#포트-열기)).

## 설정 파일 가져오기에서 파일을 찾지 못할 때

- "찾을 수 있는 디렉터리 밖입니다": 그 디렉터리를 `NGINX_MANAGER_IMPORT_ROOTS`에 적습니다.
- "관리도구 컨테이너에서 볼 수 없습니다": compose에서 manager에 같은 경로로 마운트했는지 확인합니다.
- 파일 권한: 관리도구는 UID 10101로 돌므로 그 사용자가 파일을 읽을 수 있어야 합니다.

자세한 방법은 [5장](05-import.md#찾을-수-있는-디렉터리)에 있습니다.

## "다른 사람이 먼저 저장했습니다"가 나올 때

내가 화면을 연 뒤 다른 사람이 같은 항목을 저장했습니다. 입력한 내용은 저장되지 않았습니다. 화면을 새로 고쳐 최신 내용을 확인한 뒤 다시 저장합니다.

## 비밀번호를 잊었을 때

- 다른 관리자에게 [비밀번호 재설정](12-admin.md#역할-바꾸기-비밀번호-재설정-비활성화)을 요청합니다.
- 계정이 잠겼다면 10분 뒤 저절로 풀립니다.
